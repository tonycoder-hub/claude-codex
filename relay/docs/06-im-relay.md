# IM 关口：用飞书长连接把常驻 Mac 接到手机上，以及这件事的隐私代价

写于 2026-10-22。`04-ingress.md` 解决的是「手机怎么连上 Mac 且 TLS 不落到第三方」，
`05-relay.md` 决定的是「谁和谁接上」。这份文档问的是一个不同的问题：**如果放弃 T1，
换来的是什么？** 凡事实按 **已核实 / 推断 / 未核实** 标注，核实的口径写在第 9 节。

动机是具体的：常驻 Mac 在 NAT 后面，而 Tailscale **至今没在它上面装过**
（见 `12` §2：原先写的「装不了」是条站不住的推断）。飞书/Lark 的长连接事件模式
是**出站拨号**的——没有入向端口、没有公网 TLS、没有反向代理。如果这条路成立，整个
`04-ingress.md` 的入口难题就被绕过去了，代价是私有内容要过飞书的服务器。

---

## 1. 判决

先给结论，再给出处。

| 问题 | 判决 | 依据 |
|---|---|---|
| 长连接事件订阅存在吗？出站拨号吗？ | **成立。** 自建应用可用，`POST /callback/ws/endpoint` 换一个 `wss://` 地址再拨出去 | 已核实（官方文档 + 三个官方 SDK 源码） |
| 一条消息能被反复改写以承载流式输出吗？ | **文本消息不行，卡片行。** 文本/富文本消息一生只能编辑 **20 次**；CardKit 流式更新是 **10 次/秒/卡片实体** | 已核实 |
| 卡片按钮能把决定送回同一条长连接吗？ | **有争议。** 文档说能，三个官方 SDK 的实现说不能 | **矛盾，见 §2.3** |
| 鉴权形状 | `app_id` + `app_secret` 换 `tenant_access_token`，7200 秒 | 已核实 |
| 平台会终结 TLS 吗？ | **会，而且连接建立之后的事件推送是明文** | 已核实（官方 SDK README 原话） |
| **整体可行性** | **可行，但有一处单点风险**：审批按钮这条路没被证实，所以设计里必须同时有一条**打字作答**的退路 | 见 §5 |

一句话版本：**这条路能走通，但它用隐私换入口，而且「按按钮批准」这个最想要的交互
恰好落在唯一一处文档与实现互相矛盾的地方上。**

## 2. 已核实的平台事实

### 2.1 长连接（事件订阅）

**已核实。** 官方名称就叫「长连接」。形状：

| 项 | 值 |
|---|---|
| 发现端点 | `POST {domain}/callback/ws/endpoint`，请求体字段是 **PascalCase** 的 `AppID` / `AppSecret` |
| 返回 | `data.URL`——一个带 `device_id`、`service_id` query 的 `wss://` 地址；以及服务端下发的 `ClientConfig` |
| 适用范围 | **仅自建应用**。商店应用不可用 |
| 并发上限 | **每个应用 50 条连接** |
| 处理时限 | 事件处理器必须在 **3 秒**内返回，否则平台**重推该事件** |
| 分发语义 | **集群模式，无广播**：一个应用的多条连接里，每个事件只有**随机一条**收得到 |
| 帧格式 | protobuf `pbbp2.Frame`，走 WebSocket **binary**；`method` 0=控制帧 1=数据帧 |
| 分片 | header 里的 `type` / `message_id` / `sum` / `seq` 四个字段驱动重组 |
| 心跳与重连 | 客户端 ping 默认 120 秒；重连是**固定间隔**不是指数退避，`ReconnectCount = -1` 表示永远重试 |
| 终止性错误 | `403`（forbidden）、`1000040350`（超出连接数上限）不可重连；`1`、`1000040343` 可重连 |
| ack | 客户端把入帧回写，带 `biz_rt` header 和 `{code, headers, data}` JSON，`data` 是处理器返回值的 base64 |

这些数字和字段名记在 `src/imrelay/transport.mjs` 的 `LARK_LIMITS` 与 `LARK_WS` 里。
**注意口径差别**：`LARK_LIMITS` 来自官方文档，`LARK_WS` 来自**三个官方 SDK 的源码**
——平台把长连接标为「仅 SDK 可用」并且不发布线协议规范，但 SDK 是开源的。本仓库不能
用那些 SDK（约束是只用 Node 内置），所以把名字抄在这里，将来真要写客户端就照这个写。

三条直接改变代码形状的后果：

1. **3 秒时限把「处理器不得做事」变成硬约束。** 一轮对话远超 3 秒。所以
   `InboundGate.accept()` 是**纯同步**的，只产出一个 intent 交给别人；测试里的
   `fakeLongConnection.push()` 在处理器返回 Promise 时直接抛错。
2. **去重是必需项，不是优化。** 重推会把一条打字变成 N 轮。`InboundGate` 以
   `header.event_id` 去重，而且**去重在白名单之前**——被忽略的事件重推时也不该被重新
   检查一遍。
3. **不能跑两个副本。** 集群模式无广播意味着两个副本会随机瓜分事件。

### 2.2 更新一条消息要多少钱

这是决定「流式还是攒批」的那个问题，答案分两半。

**文本/富文本消息：不可行。** `PATCH /open-apis/im/v1/messages/:message_id` 每条消息
**一生最多编辑 20 次**，且只在发出后 14 天内可改，5 QPS。20 次编辑撑不住一轮输出。

**卡片：可行，而且语义正好。** CardKit 的
`PUT /open-apis/cardkit/v1/cards/:card_id/elements/:element_id/content`：

| 项 | 值 |
|---|---|
| 频率 | **10 次/秒/卡片实体**；流式模式下声明豁免端点级 QPS 配额 |
| 内容 | **全量累计文本**，1–100,000 字符——**不是增量** |
| 顺序 | `sequence` 为严格递增的 int32 |
| 卡片 JSON | ≤ **30 KB**（超限报 `200860`，整张被拒，不是被截断） |
| `update_multi` | 只能是 `true`，流式模式下传 `false` 报 `300302` |
| 流式模式寿命 | 最后一次启用后 **10 分钟**自动关闭 |
| 卡片实体寿命 | 14 天；且**只能被发送一次** |
| 前置 | 卡片 JSON 2.0；客户端 7.20+ |

**「全量累计而非增量」是礼物不是麻烦。** 投影器本来就持有整个累计缓冲区，于是整个
子系统里**没有任何增量簿记**，一次丢包或重试会在下一次推送时自愈。`cards.mjs` 因此
返回两样东西而不是一样：便宜的 `streamContent`（只推那一个元素）和昂贵的
`card` + `shellDigest`（整张卡片）。`shellDigest` **当且仅当**流式文本之外的东西变了
才变，于是常见路径——只有文字在长——走便宜那条。

还核实到两个会咬人的细节：富文本组件的 `tag` 是**固定值 `markdown`**；按钮的回调数据
挂在 **`behaviors: [{ type: "callback", value: {...} }]`** 上，回来时在
`event.action.value`。这两点一开始查到了互相矛盾的说法（另一份材料说是 `rich_text` 和
`type: "request"`），因为渲染器的整个输出形状都压在上面，所以直接抓了两个组件参考页
对质才定下来。

### 2.3 按钮回传——**这是唯一一处文档与实现矛盾的地方**

想要的交互是：审批请求变成一行按钮，按下去，决定沿同一条长连接回来。

**支持它的证据（官方文档）**：`card.action.trigger` 被列为**恰好两个**可走长连接的
回调之一，并且需要在开发者后台的 **回调订阅**（Callback Subscription）页签里**单独**
再选一次长连接模式——事件订阅与回调订阅是两个独立的开关。

**反对它的证据（三个官方 SDK 的源码 + README + 用户 issue）**：

- Go / Python / Node 三个 SDK 的 WS 客户端在收到 `type: card` 数据帧时**都在写 ack 之前
  就 `return` 了**——于是平台在它的 3 秒窗口里拿不到任何响应。
- `larksuite/node-sdk` 的 README **明说**长连接模式支持事件订阅、**不支持**回调订阅。
- 一个用户提交的 issue 称卡片回调确实以 CARD 帧到达、被静默丢弃，表现为约 3 秒后的
  `200340`。

**判定：未核实，且必须按「可能不成立」来设计。** 平台到底把一次按钮点击打成 `event`
还是 `card`，从源码里读不出来，而本次任务不允许发起任何 API 调用，所以没有实测。

**这件事反而暴露了一个优势：本仓库零依赖，不用那三个 SDK。** 如果问题只是 SDK 的
缺陷，我们自己写的客户端同时处理并 ack 两种 `type` 就绕过去了。但如果是平台行为，
就绕不过去——而一个**未被作答的审批会永远卡住那一轮**，这是整个设计最致命的失败模式。

**所以退路是硬性的，不是可选的。** `inbound.mjs` 导出 `TEXT_DECISIONS`：

| 打字 | 决定 |
|---|---|
| `/ok` | `accept` |
| `/always` | `acceptForSession` |
| `/no` | `decline` |
| `/abort` | `cancel` |

这四个词走 `im.message.receive_v1`，那条路**没有任何争议**。于是**打字是承重的那条
路，按钮是锦上添花**，不是反过来。打字作答带不了 UUID（不能要求一个人手抄请求 id），
所以它按 lane 解析到「该 lane 里唯一待答的审批」，**并在不止一个时拒绝猜**——猜错等于
批准了一条没人批准的命令。

### 2.4 鉴权（只谈形状）

**已核实。** `POST /open-apis/auth/v3/tenant_access_token/internal`，请求体字段
`app_id` / `app_secret`，返回 `tenant_access_token` / `expire`。最长 7200 秒；**剩余
≥30 分钟时再请求会返回同一个 token**；签发新 token **不会**使旧的失效，所以提前刷新
是安全的（SDK 的余量：Go/Node 3 分钟，Python 10 分钟）。

`transport.mjs` 里 `describeTokenExchange()` **只返回字段名，永远不返回值**，并且有一
条测试断言序列化结果里不出现任何 secret 形状的东西。

### 2.5 TLS 与明文——把话说死

socket 是 `wss://`，对端是飞书运营的主机，**所以飞书终结 TLS**。这一条本来就是预期内
的，但实际情况比「终结 TLS」更直白：

> 官方 `node-sdk` README：鉴权只在连接建立时进行，后续的事件推送**均为明文数据**。

代码层佐证：三个 SDK 的 WS 客户端调用的都是**不做校验**的分发入口
（`_do_without_validation`、`needCheck: false`）。所以所谓「内置加密」就是 TLS 而已，
**在类别上不是端到端加密**。`Encrypt Key` 只对 webhook 有效，而且即使用了也仍然不是
端到端——密钥由飞书生成并持有。

此外，租户管理员可通过 `security_and_compliance-v1` 审计会话内容（消息与云文档，可查
180 天，单次跨度上限 30 天）。**这不是漏洞，是产品功能**，但它意味着「只有我和飞书
看得到」这句话也是不准确的——**我、飞书、以及我的租户管理员**。

## 3. 隐私代价：这是一次明知故犯地放弃 T1

`04-ingress.md` 的 T1 是：**TLS 不得终结在第三方**。这条方案**正面违反 T1**，不是绕过
它、不是部分满足，是放弃。诚实的记法是这样：

| | `04-ingress.md` 的 Tailscale Serve | 本文的 IM 关口 |
|---|---|---|
| TLS 终结在哪 | 本机 `tailscaled` | **飞书服务器** |
| 私有内容谁能读 | 只有本机 | **飞书；加租户管理员（180 天可审计）** |
| 入向端口 | 无（tailnet 内） | **无**（出站拨号） |
| 公网证书 | 需要 | **不需要** |
| Mac 要装什么 | Tailscale | **什么都不用**（这正是它的意义） |
| T1 | 满足 | **不满足** |

**所以这不是 `04-ingress.md` 的替代品，是它的补集。** 两者解决的是不同的人群：
Tailscale 路线给能装客户端的机器，IM 路线给**不能或不该装**的机器。把它们当竞品比较会得出
错误结论。

### 3.1 唯一真实的缓解手段：`DETAIL` 旋钮

既然内容必然过第三方，那唯一能动的就是**让多少内容过去**。`cards.mjs` 的 `detail`
是个真旋钮，不是复选框：

| 档位 | 卡片里有什么 | 适用 |
|---|---|---|
| `full` | 模型输出流进聊天；fileChange 附 diff | 内容本身不敏感时 |
| `brief` | 状态、计数、输出的一小段尾巴；**丢掉 reasoning** | 够判断「要不要走到机器前」 |
| `notify` | **没有模型输出、没有 diff**。卡片退化成纯**控制面**：说这一轮在跑、用了几个工具、什么在等批准 | 内容必须留在 Mac 上 |

`notify` 档有一处刻意的例外：**审批摘要在这一档仍然保留**。因为**一个人无法批准一条
他看不见的命令**，一张索要盲签的卡片比没有卡片更糟。测试
`a notify-detail card is a control surface that carries no model output` 断言的就是这
件事：模型输出和 diff 都不在载荷里，但命令行还在。

**推断（未核实）**：即使在 `notify` 档，元数据仍然泄漏——轮次的时刻、频率、工具类型
的序列、以及被批准的命令行本身。对一个足够有动机的观察者，这些并不弱。说清楚比假装
没有要好。

## 4. 接口决定：**并排，不是实现**

任务里问的是：IM 关口应该 (a) 实现既有的 relay 线协议、(b) 作为另一种接口并排放、
还是 (c) 两者都要。

**结论：(b)，并排。** 同意任务里那个读法，理由可以说得更锋利一点：

`05-relay.md` 第 3 节把 relay 的性质写死了——**「接通之后双向逐字转发，两个方向都不
解析」**。那是一根**字节管道**，它的价值恰恰来自盲目性：「它让一个客户端和一个服务端
在彼此从未听说过的情况下对话」。

而 IM 关口**必须解析**。它要把 `item/*` 折叠成一张卡片、要把审批请求变成按钮、要知道
一轮结束了好换个颜色。**一个必须理解载荷的东西，去实现一份以不理解载荷为卖点的协议，
是把两边的长处都丢掉。** 具体地说：relay 的两端是对称的 socket，IM 的两端是
「一条聊天消息」和「一轮对话」——**根本不是同一种基数**，一条消息对应零到多轮，一轮
对应多次卡片改写。

但它**消费** relay 的一部分，而且是经过挑选的那部分：

- `GET /ends` 当作 end 名册，直接喂给 `Dispatcher.observeEnds()`，**字段形状逐字不改**
  （`{end, busy}`）。
- 依赖 `05-relay.md` 第 3 节那条「**注册寿命 = 控制 socket 寿命，没有任何定时过期**」
  的性质——于是**不在名册里就是真的走了**，不是「暂时没说话」。调度器把缺席当权威信号
  用，这条性质不成立的话 `observeEnds([])` 就会误杀活着的 end。

所以关系是：**IM 关口是 relay 的客户端之一，不是 relay 的另一种实现。**

```
                   ┌─ web surface ──→ relay (/attach) ──→ end  （字节管道，不解析）
app-server ────────┤
                   └─ IM 关口 ───────→ app-server 客户端      （轮级调度，必须解析）
                           └── 只消费 relay 的 GET /ends 作为名册
```

## 5. 调度层：IM 关口为什么该自己拥有调度

这是「更激进」的那部分。论证很短：**一条聊天消息需要被决定的事情就是「在哪、什么时候
跑」，而这个决定的每一个输入本来就都从这里经过。** 消息属于哪个会话是消息自身的属性；
那个会话的线程归哪台常驻机器是这里持有的绑定；那台机器空不空是这里读的名册。把队列
放到别处，意味着先得把这三件事运到别处去。

同样重要的是**它不拥有什么**：线程与轮次状态在 app-server 里，经 `thread/start`、
`thread/resume`、`turn/start`、`turn/interrupt` 和流式 `item/*` 通知到达。调度器**不存
转录、不数 token、不判断一轮产出了什么**。它只存 app-server 不可能知道的三件事：
**会话到线程的绑定、队列、以及还没人作答的审批集合**。

`Dispatcher` 是纯的：没有定时器、不读时钟，每个方法收 `at`，每个后果以**效果对象**
返回给调用方去执行。于是测试能在零墙钟时间里跑完一整天的调度。

### 四个值得争论的决定

**1. 线程钉在一个 end 上，end 死了就排队，不改派。** `03-reframe.md` 把 app-server 的
线程库追到了 `CLAUDE_CODEX_HOME/state.sqlite`——**每个安装一份**。所以在另一台机器上
`thread/resume` 找不到那个线程。悄悄把会话挪到空闲 end 会**丢掉全部历史却看起来像成功
了**。于是绑定的 end 下线时那条 lane **等着**，而搬家是一个显式动作（`/end <id>`），
它会在卡片上明说上下文没了。

**2. 每条 lane 永远只跑一轮。** 协议里线程内没有并发轮次，也没有通用的 cancel，只有
`turn/interrupt`。按 lane 串行**不是策略选择，它就是协议**。

**3. 一个「忙」但不是被我们弄忙的 end，不可调度。** 常驻 Mac 同时也被它自己的桌面
应用驱动。relay 的 `busy` 是 end 的自述，调度器自己的计数是我们发起的那些。两者在
「忙，但不是我们弄的」这个方向上不一致时，**说明有人正在用那台机器，我们让开。**

**4. 待答的审批永远不会被自动决定。** 给它加个超时很容易，但两个可用的默认值都是错
的：`decline` 会在一个「拒绝和打错字不可区分」的词汇表里**静默地拒掉真实工作**，而
自动 accept 是一个**带定时器的安全漏洞**。于是一个没人答的审批会**占住它的 end**——这
是实打实的成本——缓解手段是一个提醒效果加一个显眼的「中止这一轮」按钮。**这个成本是
故意付的。**

配套的一条：被放弃的审批是**被 reject 掉**的（产生一个 JSON-RPC 错误响应），**不是**
用 `decline` 去 resolve。理由同上：resolve 成 `decline` 等于声称有个人拒绝了。

### 审批词汇表被检查了三次，这不是偏执

`03-reframe.md` 已核实：adapter 的 `normalizeDecision` 把**任何不认识的决定值静默映射
成 `decline`**。于是一个越界的值**在任何地方都不是错误**——调用成功、工具被拒、唯一的
症状是一个「什么都不肯跑」的 agent。所以：`cards.mjs` 只铸造那四个合法值；
`inbound.mjs` 在值从客户端回来时**再查一次并拒绝而非强转**；`Dispatcher.answerApproval`
查第三次。三处都从 `src/appserver/client.mjs` **import** `APPROVAL_DECISIONS`，不抄，
因为一份封闭词汇表的两个副本就是其中一个过期的方式。

## 6. 流式的可行性，收敛成一个算术

`throttle.mjs` 的 `pacingFor()` 把整个可行性论证压成一行：平台给每张卡片 10 次/秒，
留 25% 给非流式流量（新消息、完成通知、审批卡），剩下 7.5 次/秒，即**每 134 毫秒重画
一次**。手机上读起来是流畅的。

真正的坑不在频率上，在**边沿方向**上。直觉写法是前沿节流（leading-edge）：「离上次
发送超过 N 毫秒就发，否则忽略」。它**恰好有一个 bug，而且在这里是致命的**：一轮里
最后一个 delta 几乎总是落在冷却窗口内，于是被忽略，而之后再没有任何东西来触发发送——
**卡片永久停在倒数第二个状态上**。在手机上读起来就是「agent 说到一半不说了」。

所以 `CardPacer` 是**后沿合并**（trailing-edge coalescing）加一个待发修订号的高水位
标记：`#pending` **只由 `settled()` 清除，`poll()` 永远不清**。测试
`THE bug this module exists for: the final update is not dropped` 就是这条。

## 7. 原型与测试

只做了能离线测的部分。传输层是**有文档的接口加测试里的 fake**，不发任何网络请求、不
绑任何监听、不碰任何凭证。

| 文件 | 它是什么 |
|---|---|
| `src/imrelay/projection.mjs` | 把 `item/*` / `turn/*` 折叠成一个可渲染的轮次视图 |
| `src/imrelay/throttle.mjs` | 令牌桶 + 后沿合并的卡片写入节奏 |
| `src/imrelay/transport.mjs` | I/O 接缝（本身零 I/O）：限额常量、op→HTTP 纯函数、**保险丝** |
| `src/imrelay/cards.mjs` | 快照 → 卡片 JSON 2.0；`DETAIL` 隐私旋钮 |
| `src/imrelay/inbound.mjs` | 不可信载荷边界：去重、白名单、命令、决定词汇表 |
| `src/imrelay/dispatch.mjs` | 调度器：纯状态机，返回效果对象 |

测试：`node --test "test/imrelay/*.test.mjs"` → **167 tests, 167 pass, 0 fail**
（Node v22.22.0，连跑三次一致）。注意是 **shell glob 形式**，目录形式在这台机器的
Node 22.22.0 上会 MODULE_NOT_FOUND（既有问题）。

### 保险丝：这个原型不可能意外发到任何地方

任务里那句「这个原型必须不能意外发到任何地方」是这样实现的：

- `sealedSink()` 是默认值，**拒绝每一个操作**；
- `allowlistSink` 的空白名单**什么都不放行**，**没有通配符**，没有任何写法表示「全部
  放行」；
- `destinationOf()` 的 `default` 分支是**拒绝**，不是放行——一个它没有规则的新 op 被拒；
- `patchCard` 被**直接拒绝**，因为一个 message id 无法归属到某个被允许的会话；
- `InboundGate` 空白名单下把每条消息变成 `ignored`——**所以内部只读群里的任何消息都
  不可能变成一次 prompt，也不可能被转发出去**。

对应测试：`with no allowlist nothing becomes a turn and nothing can be posted`、
`an allowlisted relay still cannot write to a chat it was not given`、
`an empty allowlist accepts nothing and there is no wildcard`。
